# 视频 AI 智能监控分析平台

**阶段：单路生产运行 + 多路候选试运行** · **最近核验：2026-11-03**

## 业务目标

在既有监控体系上补齐设备不具备的智能能力：设备原生智能能给的从设备取事件，缺的部分由项目 AI 补，两条来源收敛到同一套通道身份、事件来源、规则与统计口径，避免同一件事被重复计数。

## 我的职责与技术

作为唯一人类开发参与者，与 Codex 协作完成取流、推理调度、事件模型、统计页面与现场验证。技术涉及 Python、Flask、SQLite、RTMDet/RTMPose、FFmpeg/OpenCV、CUDA GPU 池（8×T4 + 1×V100-PCIE-32GB）、ISAPI 事件订阅、Windows 计划任务与 Web 工作台。

## 已核实成果（截至 2026-11-03）

- **多路 AI 运行：** 55 项通道目录中 **47 路候选 + 1 路生产** 处于「画面新鲜、序号持续前进」状态，7 路因触发 GPU 停止线保持停用。判定依据是新鲜帧与序号推进，不看任务状态字段。
- **GPU 容量与保护：** 开发逐路重分配脚本，按 UUID 排除其它业务占卡，逐路启动后观察 120 秒，触线即停用并恢复原配置（回退后配置哈希与迁移前一致）。停止线为 GPU 计算利用率连续 30 秒达 95%、目标卡显存达 80%、整机 CPU 连续 60 秒达 90%。
- **原生事件接入：** 8 台 NVR 各起独立事件订阅任务，页面按源显示连接状态、未映射数、来源与发生/接收时间；累计收到 **4,146 条**报文，**有效业务事件入库 0 条**。
- **客流 V1：** 方向穿越人次按通道/地点、小时/日期、净流入查询并支持 CSV 导出；未配置、停用、数据缺失分区显示，不用 0 冒充。固定日抽样一路为进入 71、离开 64、净流入 7，仅代表该路该日。
- **双时间戳：** 每条事件同时保留设备发生时间（UTC）与项目接收时间（UTC）并标注时间质量；历史缺失来源标 `UNKNOWN_LEGACY`，不回填猜测值。
- **通道能力台账：** 55 项逐通道只读摸底（台账分 D 22、E 7、D+ 2、A/B/C 9、等级未核实 15）。设备直连口径 30 路可读、5 路 401、17 路不可达、3 路 404；27 路移动侦测启用且目标含人形，8 路越界/区域接口可读；NVR 逐通道规则接口 42 路返回 `notSupport`。
- **自动化测试：** 候选全量 **177 项通过**，另有 1 条第三方库弃用警告。

## 代表性工程难点

- **连接成功不等于端到端验收。** 8 个事件源都返回 HTTP 200，但收到的全是 `videoloss/inactive` 且通道号为 0、映射不到业务点位，事件库里因此 0 条有效事件。统计页面按这个口径标注，不把连接状态写成报警已验收。
- **重连退避的逻辑缺陷。** 生产单路在取流失败后按 `min(2*reconnects,30)` 秒等待，且失败计数从不清零，一次读取失败就可能挂起约 30 秒。改为正常取流满 30 秒、30 帧才清零连续失败，单文件替换 + 原件备份 + 受控重启。首次发布因「4 秒内读不到任务状态」被误判失败并自动回滚；修订后以新运行 ID 与新鲜帧为成功条件、允许 6 分钟模型加载，才真正落地。
- **只写能验证的部分。** 动作识别误报明显时先关闭正式告警，而不是靠调阈值把数字做漂亮；访客模块完成登记与配置接口，但不宣称能自动识别已登记访客。

**面试可讨论：** 为什么「任务 Running」不能当作 AI 正常的证据？原生事件接口通了但 0 条业务事件，怎么区分接线问题与设备确实没触发？显存被别的业务占满时，如何在不影响对方的前提下做扩容决策？
