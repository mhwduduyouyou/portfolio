# 企业日报数据自动化与可视化平台

**阶段：生产运行** · **首份真实业务数据：2026-07-29** · **三档无人值守上线：2026-08-27** · **最近只读核验：2026-11-03**

## 业务目标

自动采集企业业务日报，完成清洗、缓存、校验、可视化与导出，减少重复人工取数和错误覆盖。

## 我的职责与技术

作为唯一人类开发参与者，与 Codex 协作完成采集架构、数据规则、看板和上线迭代。主要使用 Python、Playwright、Edge CDP、SQLite、PyQt5/QWebEngine、ECharts、Flask 与 Windows 计划任务。

## 已核实成果（截至 2026-11-03）

- 覆盖 **6 个公司级账套 + 1 个集团账套、13 条业务线**，其中 **10 条**在采集配置中带数据源、支持自动采集，其余 **3 条**无自动采集源、走手工 Excel 导入；累计 **24,696 行**结构化明细，覆盖 **160 个**业务日期（2026-05-21 → 2026-11-03）、**173 个**字段键。
- 每日 **08:30 / 13:20 / 20:10** 三档计划任务；运行留痕 **112 轮**（2026-09-24 → 2026-11-03）：成功 **93**、跳过 **10**、失败 **9**。
- 最近一轮（2026-11-03 08:30 档）完成 **7 条**业务线、失败 **0 条**、单轮耗时 **1,079 秒**；近 12 轮单轮耗时 **807–1,100 秒**（旧记录的 830–950 秒偏低，已按实测更正）。
- **9 次失败全部为环境类**：6 次登录凭据失效、3 次浏览器会话过期，均在数十秒内返回失败且不写入缓存，没有造成数据错乱或旧数据被覆盖。
- 桌面看板与 Web 看板、Excel 导入上传服务同时在线；提供 HTML / Excel / PNG 导出。美团菜品销量为同一平台的扩展表，累计 **846 行**、**9 个**业务日期（最近一次 2026-09-12）。

## 代表性工程难点

在目标系统业务 API 不可用时，改用 DOM 采集。针对虚拟滚动重复行、汇总字段和明细混算、碎片行等问题，采用业务行键去重、数据暂存校验和原子提交，避免失败采集覆盖旧数据。

采集前先校验源与目标线的业务类型是否一致，不一致则显式跳过并记录原因，而不是把别的业务线数据写进当前缓存——宁可缺一天，也不写错一天。

调度留痕把「成功 / 跳过 / 失败」三态分开统计：跳过是配置性无源（正常），失败是环境性中断（需处理），两者混算会掩盖真实可用率。

**面试可讨论：** 为什么采集到的数据不能直接覆盖缓存？如何区别成功、失败和跳过的调度记录，并把它们变成可运算的可用率指标？
