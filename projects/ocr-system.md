# OCR 单据智能识别与审核系统

**阶段：生产运行** · **首次服务运行：2026-07-20** · **2026-08-10 起承接实际上传** · **最近只读核验：2026-11-03**

## 业务目标

对多类型业务单据的图像进行文字识别、结构化字段匹配和人工审核，使识别结果能够进入可追溯的业务处理流程。

## 我的职责与技术

作为唯一人类开发参与者，与 Codex 协作设计并交付系统，负责识别链路、问题分析、部署验证和上线后的用户反馈迭代。技术涉及 Python、Flask、RapidOCR/ONNX Runtime、PaddleOCR 领域续训、OpenCV、SQLite 和双 T4 GPU。

## 已核实成果（截至 2026-11-03）

- 累计上传 **6,879 张**影像（**22.8 GiB**）、执行 **6,885 次**识别会话，时间跨度 2026-08-10 → 2026-09-22；其中包含三轮合计约 **5,076 张**批量处理，日常实际量级约 **20–80 张/天**。
- 批量文档 **108 份**、合并批次 **21 个**，使用 **3 类**业务单据模板（按文档数分别为 92 / 15 / 1 份）。
- 产出结构化明细 **6,828 行**（其中软删除 35 行）；带低置信标记 **6,402 行**；人工修正 **266 条**留存可回溯。
- 识别服务在线：主应用 + 监督进程 + **2 个** GPU 工作进程分别绑定两张 T4（另有独立校验环境），两处部署均在监听待用。
- 专项评测口径下，端到端字段正确率经多层优化由 **11% 提升至 67%**，不代表全部生产单据的总体准确率。
- 审核闭环完成度偏低：6,828 行明细中仅 **19 行**被标记为已复核，其余仍待处理——识别能力与人工复核的实际投入并不匹配。

## 代表性工程难点

手写车号、司机姓名与数字汉字混排可能出现粘连及吞字。针对这一问题，结合识别参数、字段分配、领域模型续训和规则纠偏优化。部署侧通过 GPU 引擎池控制显存与实例竞争，排查跨池漂移和池空恢复问题。

每个识别结果都带低置信与模板不确定性标记，供人工复核优先排序；修正记录按「原值 / 修正值 / 模板 / 影像名」留存，使 266 条修正可以回放成评测样本，而不是只当作手工改数。
